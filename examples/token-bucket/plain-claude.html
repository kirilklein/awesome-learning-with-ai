How a token bucket rate limiter works

A rate limiter decides, for each request that arrives, whether to let it through. A token bucket is a common way to make that call. It lets a client send a short burst, but holds it to a fixed rate over time.

The rules

  1. A bucket holds up to 10 tokens. It starts full.
  2. Tokens are added at 2 per second, one every half second. A full bucket stays at 10. Extra tokens are dropped.
  3. Each request takes one token and goes through. If the bucket is empty, the request is rejected. An HTTP API would usually answer with status 429 Too Many Requests.

That is the whole algorithm. The rest of this page lets you watch it run.

What to notice

  • The bucket size is the largest burst. A full bucket can serve 10 requests at the same instant. The 11th is rejected.
  • The refill rate is the long-run limit. Once the stored tokens are gone, a request can only use a token that has just arrived. Tokens arrive at 2 per second, so 2 requests per second get through, no matter how many are sent.
  • Quiet time is saved up, but only to a point. A client that sends nothing for 5 seconds earns a full bucket. Waiting longer earns nothing more.
  • A rejected request costs nothing. It takes no token, so a client that keeps hammering does not push the bucket into debt. It is also not queued. The client has to try again later.

In code

You do not need a timer that drips tokens in. Store the token count and the time of the last check. When a request arrives, work out how many tokens were earned since then. 

const CAPACITY = 10;   // tokens
const REFILL = 2;      // tokens per second

function allow(bucket, now) {
  const seconds = (now - bucket.last) / 1000;
  bucket.tokens = Math.min(CAPACITY, bucket.tokens + seconds * REFILL);
  bucket.last = now;

  if (bucket.tokens < 1) return false;   // reject with 429
  bucket.tokens -= 1;
  return true;
}

A real service keeps one such bucket per client, keyed by API key or IP address, so one busy client cannot use up everyone else's tokens.
