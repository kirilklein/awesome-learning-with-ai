Rate limiting primer

How a token bucket rate limiter works

Most public APIs cap how fast a client may call them. The token bucket is one of the most widely used ways to enforce that cap. It lets short bursts through, holds the long-run rate steady, and fits in under twenty lines of code.

This page follows one bucket throughout: it holds 10 tokens and refills at 2 per second.

About 8 minutes · three demos · a short quiz

01 · The problem

A server can only do so much per second

A service has a fixed amount of CPU, memory and database connections. One client stuck in a retry loop, or one script fetching every page it can find, can use all of it and slow the service down for everyone else.

A rate limiter sits in front of the service and decides, for each incoming request, whether to let it through. Requests over the limit are turned away immediately, usually with HTTP status 429 Too Many Requests, so the server spends almost nothing on them.

The difficulty is writing a rule that is strict about sustained load and still tolerant of normal behaviour. Real clients are bursty. A page load fires eight calls at once, then nothing for a minute. A rule that allowed exactly one request every half second would reject most of that page load, even though the client averages far less than the limit.

02 · The rule

The whole algorithm is three rules

The limiter keeps a bucket of tokens for each client. A token is permission to make one request.

  1. The bucket holds at most 10 tokens. It starts full.
  2. Tokens are added at 2 per second, one every half second. A token that arrives at a full bucket is discarded.
  3. Each request takes one token and is served. If there is no token to take, the request is rejected.

Saved tokens are what make bursts possible. A client that has been quiet has a full bucket and can spend all 10 at once. A client that never stops gets only what the refill provides.

    The partly filled disc at the top of the stack is the next token on its way: half a second from nothing to usable. Whatever rate you pick above 2, the accepted count settles at 2 per second once the saved tokens are gone. A larger bucket would only postpone that moment.

    The arithmetic behind the numbers

    At r requests per second, with r above 2, the bucket gains 2 tokens and loses r each second. A full bucket therefore lasts about 10 ÷ (r − 2) seconds: 5 seconds at 4 per second, under 2 seconds at 8.

    An empty bucket refills in 10 ÷ 2 = 5 seconds if no requests arrive.

    Raise capacity and more of the burst gets through, while the sustained stretch barely changes until the bucket is bigger than the burst itself. Raise the refill rate and the sustained stretch follows it. In practice the two are chosen separately: capacity from the largest burst a well-behaved client makes, refill rate from the load the service can carry for that client indefinitely.

    A common misreading. “2 per second” sounds like a ceiling on every individual second. With this bucket a client can get 12 requests through in one second: the 10 saved tokens plus the 2 that arrive during it. Over any stretch of T seconds, the most that can pass is capacity + refill rate × T.

    05 · In code

    The implementation needs no timer

    Nothing adds tokens in the background. The bucket stores two values, the token count and the time it was last updated, and works out the refill it is owed whenever a request arrives.

    import time

class TokenBucket:
    def __init__(self, capacity=10, refill_rate=2.0):
        self.capacity = capacity
        self.refill_rate = refill_rate   # tokens per second
        self.tokens = capacity           # start full
        self.updated = time.monotonic()

    def allow(self):
        now = time.monotonic()
        elapsed = now - self.updated
        earned = elapsed * self.refill_rate
        self.tokens = min(self.capacity, self.tokens + earned)
        self.updated = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False
    Refill on demand
    earned is the number of tokens that accumulated since the last call. min() enforces the capacity, so a long idle period never yields more than 10.
    Fractions are kept
    A request 0.3 seconds after the bucket emptied finds 0.6 of a token and is rejected. The 0.6 stays, and a request 0.3 seconds later is accepted.
    Two numbers per client
    That is the entire state. The demos on this page run this same arithmetic in JavaScript.
    One bucket per client, and where it lives

    A limiter keeps a separate bucket for each key it limits by: an API key, a user ID or an IP address. One client draining its bucket has no effect on another.

    The class above is for a single process and is not thread-safe. With several servers behind a load balancer the buckets usually move to a shared store such as Redis, and the read, refill and decrement must run as one atomic step. Otherwise two servers can spend the same token.
